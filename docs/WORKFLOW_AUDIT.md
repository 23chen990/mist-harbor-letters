# 《雾港来信》项目工作流与数据源审计

审计日期：2026-08-29  
审计范围：项目仓库内全部文件（不含 `.git` 内部对象）；只读检查 XLSX、CSV、JSON、Markdown、GDScript、TSCN、Godot 配置/缓存、Shell、Python、MJS 与 PNG 资源。  
本次改动：仅新增本文件；未修改剧情、代码、工作簿、运行数据或其他现有文件。

## 审计摘要

当前仓库同时存在两套互相矛盾的数据架构：

1. **实际运行架构**：UUID 路径工作簿的 `剧情剧本`（21 列）→ 同步器 → `content/程序生成_请勿手改/剧情剧本.csv` → Godot。
2. **工作簿声明的 v4.1 架构**：作者参考表 → `RUN_NODES` / `RUN_CHOICES` / `STATE_SCHEMA`；但仓库中没有生成这些运行表的现行工具，Godot 也完全不读取它们。

因此，工作簿的“运行说明”不是当前代码的真实数据流。当前 CSV 与工作簿 `剧情剧本` 完全一致（373 条数据行），但 CSV 无法通过现有剧情链接校验，项目启动后会显示“剧情表无法加载”。

## 读取可靠性与限制

| 类型 | 读取结果 | 限制 |
|---|---|---|
| `.xlsx` 及工作簿备份 | 7 份均可可靠导入；可读取工作表、单元格、表头、有效区域和公式 | 7 份均无公式；本审计没有把样式、颜色或视觉排版当作剧情事实 |
| `.csv` / `.bak` CSV | 可用 UTF-8-SIG 与标准 CSV 规则可靠读取 | 多行单元格已被同步器转义；解析时按 CSV 而非按物理行计数 |
| `.json` | 2 份均为有效 JSON，可可靠读取 | 均位于临时工作目录，且无运行时引用 |
| `.yaml` / `.yml` | 仓库内不存在 | 无可审计文件 |
| `.md` / `.gd` / `.tscn` / `.cfg` / `.godot` / `.import` / `.command` / `.py` / `.mjs` | 文本均可可靠读取 | `.godot` 下的内容属于编辑器缓存，不应提升为项目规则 |
| `.png` | 240 份均能解码；可确认尺寸与哈希 | 它们是工作表预览，不适合逐字 OCR 后当作事实源；未据图片补设定 |
| `.DS_Store`、`.godot/uid_cache.bin` | 只能可靠确认二进制类型、大小和存在性 | 无法可靠提取项目语义；未据其内容推断 |
| `.uid`、`.md5` | 可读为资源 UID/导入哈希 | 只用于 Godot 缓存关联，不是剧情或规则源 |

## 二、当前实际数据流

### 1. 游戏启动后的真实读取路径

```text
project.godot
  → scenes/main.tscn
    → scripts/main.gd
      → scripts/game_state.gd
      → scripts/story_repository.gd
      → content/程序生成_请勿手改/剧情剧本.csv
```

- `project.godot:14` 指定 `scenes/main.tscn`。
- `main.tscn:3,12` 只挂载 `scripts/main.gd`。
- `scripts/main.gd:34` 直接读取 CSV；启动时不打开 Excel、JSON、YAML、Markdown 或工作簿的 RUN 表。
- `scripts/story_repository.gd` 读取 CSV 的 21 列，建立 stage、检查自动 ID 和 `下一话题`。
- `scripts/game_state.gd` 解释条件、写入知识/变量并保存选择历史。

### 2. 剧情文本、选择与变量如何进入游戏

- **剧情文本**：UUID 工作簿 `剧情剧本` 的 `NPC台词`、`玩家可选台词`、`画面表现` → 同步 CSV → 运行器。
- **选择与分支**：同一表的 `玩家可选台词`、`出现条件`、`选择结果`、`状态写入（不显示）`、`下一话题` → CSV → `story_repository.gd` / `game_state.gd`。
- **玩家知识**：`玩家因此知道什么` 和状态动作共同进入 `player_knowledge`；同时 `game_state.gd` 还硬编码 `KNOWLEDGE_CATALOG`。
- **角色知识**：工作簿 `CHAR_KNOWLEDGE` 当前不被运行时读取；角色知识只以 CSV 中的条件/状态约定和作者自律存在。
- **世界事实**：工作簿 `FACT_SCHEMA` 当前不被运行时读取；`game_state.gd` 另有 4 条硬编码 `WORLD_TRUTHS`。
- **变量定义**：运行时允许 CSV 动态创建 `technical_values` / `technical_collections`，没有按 `STATE_SCHEMA` 做严格登记。

### 3. Excel 同步的实际效果

```text
打开剧情工作簿.command
  → 只打开 UUID 路径 XLSX

同步剧情工作簿.command
  → tools/同步剧情工作簿.gd
    → tools/xlsx_story_importer.gd
      → 只读取“剧情剧本”前 21 列
      → 临时生成并校验 CSV
      → 备份当前 CSV 为“剧情剧本.csv.上次同步.bak”
      → 覆盖当前 CSV
```

- Excel **不会覆盖 JSON、YAML、RUN_NODES、RUN_CHOICES、STATE_SCHEMA、FACT_SCHEMA 或 CHAR_KNOWLEDGE**。
- 仓库没有 YAML；两个 JSON 只是旧抽取物，无运行时引用。
- 不存在双向同步：CSV 的改动不会回写 Excel；RUN 表的改动不会回写 `剧情剧本`；两个现行 XLSX 也不会自动互相同步。
- 同步只保留一个 CSV 备份，无法形成完整版本历史。

### 4. 哪些修改不会反映到运行时

- 只修改 `outputs/雾港来信_剧情作者工作簿_v4.1.xlsx`，但不复制到 UUID 路径。
- 修改 UUID XLSX 后不运行同步命令。
- 修改工作簿中除 `剧情剧本` 外的任何工作表，包括 `RUN_NODES`、`RUN_CHOICES`、`STATE_SCHEMA`、`FACT_SCHEMA`、`CHAR_KNOWLEDGE`、`AI资源清单`、`最新世界真相`。
- 修改 v5/v6、CURRENT_TRUTH、DECISIONS、岗位文件、README、研究/复盘表、JSON 抽取物或 PNG 预览。
- 修改工作簿备份或 CSV 备份。

### 5. 哪些旧文件仍被引用

- README 和 10 个以上测试仍把 v3.4.3、367 行、父子关系、沈家旧宅和“前序·归家”作为现行口径。
- `scripts/main.gd` 第一章入口仍是“前序·归家”，并硬编码旧宅/父子热点。
- `scripts/game_state.gd` 默认 stage 仍是“前序·归家”。
- 五个 Python 迁移脚本仍引用仓库外 Downloads 工作簿和非 UUID v4.1 工作簿，并内嵌旧名/旧设定。
- 历史 MJS 构建器仍可生成 v2.7/v3.4.3 父子版本。
- v6 自身引用仓库外 `~/.cursor/plans/...` 和仓库中不存在的“序章与第一章完整剧情信息树 v6”；这两个更高/互补来源无法在本次仓库审计中验证。

## 三、重复和冲突

### 1. 数据级重复

| 类型 | 发现 | 风险 |
|---|---|---|
| 重复现行工作簿 | 两份现行 XLSX SHA-256 完全相同，但只有 UUID 路径被打开和同步 | 任一份被单独编辑后立即分叉；文件名均像“正式版” |
| 工作簿/CSV 重复 | `剧情剧本` 373 行与当前 CSV 在规范化后完全一致 | 合理的生成关系，但 CSV 不应被当成第二编辑源 |
| 作者层/运行层重复 | `剧情剧本` 有 373 节点；`RUN_NODES` 有 357 节点；`RUN_CHOICES` 再复制其中 102 个选择 | 三套可编辑副本没有可执行生成链，会漂移 |
| 废弃节点重复 | `剧情剧本` 比 `RUN_NODES` 多出的 16 个 ID，恰好等于 `ARCHIVE_废弃逻辑` 的 16 个 ID | 工作簿说明称这些节点永不运行，但实际同步器仍把它们全部写入 CSV |
| 预览重复 | 240 张 PNG 只有 74 个唯一哈希 | 临时审阅产物占据仓库并混淆“素材”概念 |
| 历史结构重复 | 5 个 XLSX 备份、2 个 JSON 抽取、1 个 CSV 备份、多个旧 MJS/Python 脚本 | 旧版本可被误开、误同步或重新生成 |

### 2. 重复台词与场景

当前自动 ID 无重复；当前 `剧情剧本`、CSV、RUN_NODES、RUN_CHOICES、STATE_SCHEMA、FACT_SCHEMA 的主键均唯一。

发现 4 组完全相同台词：

| 台词 | ID | 判断 |
|---|---|---|
| “您稍等。” | `S0007` / `S0009` | 姓名/递信两条互斥入口分支，重复可能有意 |
| “林班主让您进去。” | `S0008` / `S0010` | 姓名/递信两条互斥入口分支，重复可能有意 |
| “成。到了。” | `S0024` / `S0031` | 条件不同，可能有意 |

### 3. 变量、知识和 ID 冲突

## 五、现有工作流问题

### 1. 旧母版重新覆盖风险

- 两份现行工作簿同名不同路径，当前恰好同哈希，但没有同步锁或源哈希检查。
- Python 脚本会直接改写非 UUID v4.1 和 Downloads 外部文件；历史 MJS 会生成或覆盖旧父子版本。
- 同步器只看固定路径和 21 列，不检查工作簿版本、审批状态、v6 关系、RUN 表新旧或是否来自 `.bak`。
- CSV 只保留一次备份，且仓库没有 Git 提交；误覆盖后没有可靠项目级回滚。

### 2. GPT 与 Codex 的最新信息传递

- 当前依赖聊天上下文、v6 长文、CURRENT_TRUTH、工作簿作者表和外部计划；没有自动生成的同一快照。
- v6 引用仓库外 Cursor 计划与未收录剧情树，Codex 无法仅凭仓库确认最高优先级内容。
- CURRENT_TRUTH 是人工摘要，会形成第二母版风险；DECISIONS 为空，无法判断哪些聊天结论真正获批。
- 没有源文件哈希、生成时间、Git 提交、审批状态和“本次允许修改范围”的统一上下文包。

### 3. 审批与范围约束

- 无任务卡、无 `DRAFT/APPROVED` 状态、无批准人、无允许修改文件清单。
- 迁移报告可直接写“已完成”，但没有独立验收门；现状证明报告结论与可执行状态不一致。
- 岗位文件已有禁止事项，但没有根目录 `AGENTS.md` 作为 Codex 首入口，也没有强制指向权威范围和任务卡。

### 4. 自动剧情校验不足

已有校验：21 列存在、自动 ID 唯一、`下一话题` 存在。  
缺少或失效：

- 运行入口 stage 存在性；当前未检查，导致“前序·归家”缺失。
- archive 节点不得进入运行数据；当前 16 条仍进入 CSV。
- 状态 ID 必须登记；当前 8 个精确缺失，运行时仍会动态创建。
- 条件语法与工作簿规范一致性。
- 角色知识/秘密释放自动对照 `CHAR_KNOWLEDGE`。
- `玩家必须已经知道什么` 列不存在导致知识前置检查失效。

## 六、最小改造方案

本节仅提出方案，不执行。

### 1. 最少文件结构

```text
AGENTS.md                         # Codex 唯一入口，短；只指路和限制
README.md                         # 玩家/开发者运行说明
docs/
  剧情修订稿_v6_人物与前史.md     # 候选作者层设定源（需用户确认边界）
  DECISIONS.md                    # 已确认决策历史

  generated/
    GPT_CONTEXT_PACK.md           # 自动生成，只读，不是事实源

    VISUAL_BIBLE.md               # 后续视觉圣经

  <唯一确认的工作簿路径>.xlsx      # 场景对白/分支作者源

```

不新增新的剧情母版。研究材料如后续新增，应放 `docs/research/` 并在文件头声明“建议，不具权威”；聊天内容必须先进入待审批任务卡或决策草案，不能直接进入正式设定。

### 2. 根目录 `AGENTS.md` 建议内容

保持简短，只包含：

- 当前任务卡路径与状态；没有 `APPROVED` 不得修改。
- 唯一允许修改的文件范围。
- 世界/人物、对白、变量、知识、素材、决策分别指向哪个权威范围。
- 生成物禁止手改；岗位文件和研究文档禁止成为事实源。
- 冲突必须写“需要用户决定”，禁止自动合并。
- 修改前记录 Git 提交和工作簿 SHA-256，修改后运行校验与 Godot smoke test。

### 3. `GPT_CONTEXT_PACK.md` 生成方法

建议使用一个只读生成脚本，从已确认源提取而不是人工维护：

1. 读取根 `AGENTS.md`、当前已批准任务卡、`DECISIONS.md` 中“已确认”记录。
2. 提取 v6 中用户确认的权威章节；未确认/待定/已否决分区分开输出。
3. 从唯一工作簿只提取与任务相关的 `剧情剧本` 行，以及结构化的 `FACT_SCHEMA`、`CHAR_KNOWLEDGE`、`STATE_SCHEMA` 条目。
4. 附加源文件绝对项目相对路径、SHA-256、Git commit、生成时间、任务 ID 和审批状态。
5. 自动标注冲突，不做合并；若源哈希变化或任务未批准，生成失败。
6. 输出到 `docs/generated/GPT_CONTEXT_PACK.md`；文件头写明“自动生成、禁止手改、不能覆盖正式源”。

这样 GPT 与 Codex 使用同一可复核快照，而不是互相转述聊天结论。

### 4. 任务卡状态流程

建议状态：

```text
DRAFT
  → SCOPE_REVIEW
  → USER_APPROVED
  → IN_PROGRESS
  → CONTENT_REVIEW / CODE_REVIEW
  → USER_ACCEPTED
  → SYNCED
  → VERIFIED
  → CLOSED
```

每张任务卡至少包含：任务 ID、目标、权威依据、明确不做、允许修改文件、禁止修改文件、源哈希/Git 提交、用户批准记录、输出文件、验证命令、回滚点、冲突与待决定项。只有 `USER_APPROVED` 后才允许写入；剧情和代码分别审阅，避免“机械迁移完成”被误认成剧情批准。

### 5. 剧情与 Godot 自动校验建议

同步命令改成“先生成到临时目录，全部通过后再覆盖”：

- 工作簿路径/哈希与任务卡一致，拒绝 `.bak` 和未批准副本。
- `剧情剧本` ID 唯一，所有 `下一话题` 和章节入口存在。
- `ARCHIVE_废弃逻辑` ID 不得进入生成 CSV。
- 所有状态 ID 精确存在于 `STATE_SCHEMA`；禁止运行时静默创建近似变量。
- 条件语法只允许一套，并有解析测试。
- 玩家知识、角色知识和世界事实分别校验；秘密释放对照 `CHAR_KNOWLEDGE`。
- 检测相同文案且条件相交的重复选择。
- 检测 v6 已否决关键词与旧关系回流，但只报错，不自动改文案。
- CSV 生成后在临时项目副本运行 Godot 基础启动、全测试、第一章入口与一条最短流程；全部通过才替换正式 CSV。
- 输出机器可读校验报告，包含源/输出哈希、行数、失败 ID 与测试结果。

### 6. 视觉圣经、镜头表和素材清单位置

- 视觉圣经：后续放 `docs/visual/VISUAL_BIBLE.md`，记录时代、色彩、材质、构图、人物轮廓、禁用风格和参考来源。
- 镜头表：优先在唯一工作簿新增一张结构化 `镜头表`，用场景 ID/节点 ID 关联 `剧情剧本`，避免另建第二剧情文档。

商业假设先写成任务卡或 DECISION 提案，经过：假设 → 指标 → 试玩/商店页实验 → 数据 → 用户确认 → `DECISIONS.md`。竞品复盘只能提出假设，不能直接改变正式剧情或商业策略。
