# 《雾港来信》AI 团队轻量调度手册

> 文档性质：工作流程规则，不是剧情事实源、机制事实源或商业结论。
>
> 上位规则：根目录 `AGENTS.md`。本手册与其冲突时，以 `AGENTS.md` 为准。

## 1. 目标与默认工作方式

用户只需要向一个入口下达目标。当前主 Codex 默认担任**调度员**，负责读取范围、拆分任务、选择岗位、分配文件 owner、汇总分歧、安排验证，并向用户提交一份最终报告。用户不需要逐个管理岗位或代理。

岗位或子代理是临时执行单元，不拥有独立事实权。它们的报告、研究、推断和建议都不能覆盖权威剧情或已确认决策。

默认流程：

```text
用户命令
→ 调度员建立任务包并选择档位
→ 读取权威文件与可复用研究
→ 分配岗位、文件 owner 与验收人
→ 并行调查 / 审查 / 实现
→ 调度员合并证据、保留分歧
→ 必要时进入用户审批门
→ 获准后实施
→ 独立 QA 验证
→ 统一交付
```

## 2. 三档执行强度

调度员按风险自动选择最低足够档位。用户可以明确要求升档；降档不得绕过 `AGENTS.md` 的正式修改闭环。

| 档位 | 适用情况 | 默认编排 | 交付要求 |
|---|---|---|---|
| `fast` | 只读查询、状态说明、文档定位、单文件低风险整理；不改变正式剧情、人物、核心机制或商业策略 | 调度员或一个相关岗位；通常不启用独立 QA | 结论、依据、未验证项；如有修改仍列文件与验证结果 |
| `standard` | 局部实现、工具或测试修改、跨文件同步、常规缺陷修复、局部体验评估；影响可界定且不改正式事实 | 一个主 owner，加相关审查岗位；有实现时加入 `programmer`，由独立 `qa` 验证 | 完整任务包、owner 清单、修改摘要、冲突、验证命令与结果 |
| `formal` | 核心剧情、人物、核心机制、商业策略或 Demo 重大改动；权威冲突；大范围迁移 | 至少 `narrative`、`continuity`、`playtest`、`commercial_reviewer`；涉及对白加入 `dialogue`，涉及实现加入 `programmer` 和独立 `qa` | 正式审批闭环、各岗位报告、影响范围、用户确认记录、独立 QA 与统一交付 |

“只读”不自动等于 `fast`。如果检查覆盖完整章节、多个数据层、多个岗位或独立 QA，则使用 `standard`；单点定位和小范围说明才使用 `fast`。

出现下列任一情况时必须升为 `formal`：改变人物动机或关系、世界事实、核心因果、信息释放顺序、核心玩法规则、主角动词、Demo 主结构、定价或发行等正式商业策略。

## 3. 岗位路由

调度员根据任务内容自动选择 `roles/` 中的岗位；岗位文件规定方法与边界，本手册不重复替代。

| 任务信号 | 主岗位 | 常见协作岗位 |
|---|---|---|
| 剧情结构、冲突、选择、节奏、玩家主动性 | `narrative` | `continuity`、`playtest`、`commercial_reviewer` |
| 时间线、人物关系、线索来源、知识边界、旧版本残留 | `continuity` | `narrative`、`dialogue`、`qa` |
| 台词、称谓、口吻、潜台词、对白信息释放 | `dialogue` | `continuity`、`narrative` |
| 可理解性、推理公平性、交互反馈、选择意义 | `playtest` | `narrative`、`commercial_reviewer`、`qa` |
| Demo Hook、差异化、商店页、Trailer、定价、发行 | `commercial_reviewer` | `playtest`、`narrative` |
| Godot、GDScript、工具、导入、数据迁移、自动化 | `programmer` | `qa`；涉及内容时加入对应内容岗位 |
| 测试、回归、数据完整性、复现、验收 | `qa` | 不兼任被验收改动的 owner |

一个代理可以在小任务中承担多个相容岗位视角，但必须分别给出结论。核心改动的关键审查不得由单一代理自审自批。

## 4. 任务包与范围锁

调度员在开始写入前使用 `docs/templates/AI_TASK_PACKET.md` 建立任务包，至少明确：

- 唯一目标与验收标准；
- 执行档位和选用岗位；
- 权威依据、研究依据及其角色；
- 允许修改文件、禁止修改范围；
- 每个文件唯一 owner；
- 是否触发正式修改审批门；
- 验证命令、回滚点、阻塞条件。

聊天中的临时想法只能进入“提案 / 待确认”，不能被填写成“已确认事实”。任务执行中发现范围外问题时，只登记，不顺手修改。

任务状态采用轻量集合：

```text
DRAFT → READY → IN_PROGRESS → REVIEW → VERIFIED → CLOSED
                   └→ WAITING_USER / BLOCKED
```

- `READY` 表示目标、范围、owner 和验收方式已明确，不代表正式内容已获批准。
- 正式改动必须另有“用户明确确认”记录才能实施。
- `BLOCKED` 不等于失败；必须写明解除阻塞所需的最小条件。

## 5. 并行协作与单文件 owner

只有依赖关系清楚、输出可独立验收的任务才并行。推荐并行的是只读审查、不同模块实现、研究与测试设计；不推荐并行编辑同一剧情段落、同一工作簿或同一代码文件。

执行规则：

1. 每个可写文件在同一时段只能有一个 owner。
2. 非 owner 可以只读检查并提交建议，不得直接编辑该文件。
3. 共享工作簿视为一个文件；按工作表分工仍须由单一 workbook owner 汇总写入。
4. 生成物由生成流程负责，不设人工编辑 owner；`content/程序生成_请勿手改/` 禁止手改。
5. 任务有前置依赖时，后续 owner 等待前置输出确认后再写入。
6. 发现他人已有改动时先兼容，不回退、不覆盖，也不把不明改动据为己有。
7. 调度员负责最终合并；合并是整合证据与改动，不是通过多数票决定剧情事实。
8. 用户要求“不改文件”时，必须把缓存、导入产物、`user://` 数据和测试临时文件纳入边界；会产生写入的检查应在临时副本中运行，或在任务包中明确获得这类写入授权并设置前后比对。

## 6. 研究复用与过期规则

先读取 `research/KNOWLEDGE_INDEX.md` 定位可复用资产，再按当前问题读取原文。索引只存元数据，不复制研究结论，也不是第二个事实源。

涉及推理、互动或信息释放时，先读取：

- `research/COMPETITOR_INDEX.md`
- `research/DESIGN_PATTERNS.md`
- `research/COMMERCIAL_STRATEGY.md`

先搜索已有记录，再决定是否新增研究。新研究使用 `docs/templates/AI_RESEARCH_RECORD.md`，必须记录问题、来源、日期、结论类型、适用范围、过期条件和采纳状态。

可以直接复用的条件：

- 原问题与当前任务一致；
- 来源可追溯，适用范围明确；
- 没有触发文档所列过期条件；
- 未与当前权威文件或已确认决策冲突。

必须复核或重新研究的情况：

- 市场、价格、平台规则、工具版本、玩家趋势等时效性信息已过复核日期；
- 产品阶段、目标玩家、核心机制或剧情结构发生重大变化；
- 原记录没有来源、没有日期、只剩结论，或不同研究互相冲突；
- 用户明确要求最新资料。

研究结论始终是“建议 / 证据 / 假设”，不是正式剧情、机制或商业事实。即使研究仍有效，也必须经过正式审批门才能改变正式内容。过期记录不删除，在研究记录和 `research/KNOWLEDGE_INDEX.md` 中统一标记为 `needs_revalidation` 并说明原因。

## 7. 正式修改审批门

凡影响正式剧情、人物、机制或商业策略，必须遵循根 `AGENTS.md` 的闭环：

```text
发现问题
→ 读取权威文件
→ 提出修改及影响范围
→ 用户明确确认
→ 更新 DECISIONS.md
→ 必要时同步 CURRENT_TRUTH.md
→ 修改运行数据 / 代码
→ 独立验证
```

“继续做”“优化一下”“按建议处理”只有在上下文能唯一确定具体提案、影响文件与范围时才算明确确认；否则调度员应把多个待决项集中成一次审批请求。

审批请求至少包含：

- 当前问题和可定位证据；
- 拟改变的正式内容；
- 受影响的剧情、数据、代码、测试和商业环节；
- 不修改方案与备选方案；
- 需要用户确认的准确句子或选择。

未获确认时，可以继续不依赖该决定的只读调查、测试设计和风险分析；不得提前落地受影响内容。

## 8. 岗位报告与合并

各岗位使用 `docs/templates/AI_ROLE_REPORT.md` 返回结构化报告。调度员合并时：

1. 去除重复问题，但保留每条独立证据。
2. 区分“已证实事实、实现现状、推断、建议、待确认”。
3. 对分歧按权威来源核对，不用投票解决。
4. 无法裁决的分歧保留双方观点、影响与所需证据，提交用户确认。
5. 建议只有进入批准的任务包后才变成实施项。
6. 最终报告必须列出修改文件、依据、未解决冲突、验证命令与结果。

严重度建议统一为：

- `P0`：数据损坏、安全风险或完全无法继续。
- `P1`：主流程阻塞、权威冲突、重大内容或体验错误。
- `P2`：局部功能、连续性或体验问题，有绕行方式。
- `P3`：低风险改进、可读性或维护性建议。

## 9. 独立 QA

`standard` 的实现改动和所有 `formal` 改动默认由未担任对应文件 owner 的 `qa` 验证。QA 只验证和报告，不为让测试通过而修改剧情、代码、工作簿或生成数据。

QA 必须：

- 按任务包中的权威预期与验收标准测试；
- 给出可复现命令、步骤、预期、实际和证据；
- 区分真实实现缺陷、数据缺陷、环境阻塞、资料冲突和过期测试；
- 覆盖相关负向路径，不只检查理想主线；
- 如无法建立可靠预期，标记“待确认 / 未验证”，不得猜测通过。

修改 owner 可以修复 QA 报告的问题，但修复后必须由 QA 重新验证。自测结果可以附加，不能替代独立 QA。

## 10. 失败、冲突与阻塞

出现以下情况时停止受影响的写入，并继续进行不受影响的安全工作：

- 权威文件缺失、无法可靠读取或彼此冲突；
- 需要从 v5、备份、NPC 证词、实现残留、研究建议或常识补写正式事实；
- 修改超出允许文件或没有 owner；
- 正式修改尚未获得明确确认；
- 验证可能覆盖用户数据而没有隔离副本或回滚点；
- 只能通过改剧情事实、删除测试或放宽正确断言才能通过。

阻塞报告必须包含：已完成内容、阻塞证据、受影响范围、未受影响工作、需要用户提供的最小决定。失败测试必须原样报告，并明确它属于过期测试、真实缺陷、资料冲突还是环境问题；无法分类时写“待确认”。

## 11. 用户命令示例

用户无需指定岗位，以下命令即可触发调度：

```text
检查第一章当前是否可完整试玩。先只读分析，自动安排岗位，给我一个合并报告，不改文件。
```

```text
修复已确认的启动断链。允许修改相关 Godot 脚本和测试，不改剧情、工作簿和生成 CSV；你负责分工并让独立 QA 验收。
```

```text
评估序章 Demo 的 Hook、推理公平性和信息释放。复用现有竞品研究，只有资料过期时才补调研；任何剧情或机制建议先集中让我确认。
```

```text
把我刚确认的提案按正式流程落地：先记录决策，再同步权威摘要、作者入口和实现，最后做完整回归并报告所有失败。
```

```text
继续推进第一章 Demo。你担任调度员，选择合适档位和岗位；范围内的实现自行推进，涉及正式剧情、人物、核心机制或商业策略时集中向我审批。
```

## 12. 每次统一交付格式

最终交付至少包含：

```markdown
## 结果
- 是否完成：
- 执行档位与岗位：

## 修改文件
- `路径`：摘要

## 依据
- 权威文件 / 已确认决策 / 实现证据：

## 未解决冲突与待确认
- 无 / 条目

## 验证
- 命令：
- 结果：通过 / 失败 / 阻塞
- 失败分类：真实缺陷 / 过期测试 / 资料冲突 / 环境问题 / 待确认
```
